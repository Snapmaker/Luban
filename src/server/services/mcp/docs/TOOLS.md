# Luban MCP tool surface

Terse per-tool reference. Machines: A350 = CNC, F350 = printer. Staged motion needs
one operator click on the confirm page; direct-call exceptions are governed by
`cnc-motion-rules`. Results
quote coordinates with their frame (machine vs work). Call `get_stored_state` first in a fresh
session.

For a compact workflow and exact camera operation fields, see
[camera operations](../../../../../.agents/skills/cnc-camera-operations/SKILL.md).
One approval covers a complete bounded program/sequence; do not split safe internal steps into
separate confirmations. Unhomed transport/procedures refuse; `home` raises Z first and turns B.

## Orientation and status (read-only)

- `get_stored_state` — everything known in one call: calibrations, landmarks, tool region, limits, camera (incl. `camera.stream.stream_url`, the operator's live view), connection, probe feed. Start here. `connectedMachine` is `{identifier, type, hasZ}`; every landmark and calibration carries `machineScope` (`machineIdentifier`, `legacy`, `appliesToConnectedMachine`) and the top-level `machineScope` lists which records apply to the connected machine and which do not; `limits.travel` is the model-plus-fudge box the planners allow, `limits.travelFudge` the setting behind it, `limits.zLawsApply` whether the Z laws mean anything here; `geometry.travel` says which machine the stated travel belongs to.
- `get_connection_status` — is Luban connected to a machine, over what channel.
- `get_machine_profile` — kinematics, work envelope, toolhead module offsets and `connectedHead` (`headType`, `toolHead`, possibly null). `toolHeads` lists compatible heads, not the currently fitted one; generic `headType: "cnc"` alone cannot choose thread-milling spindle mode. Also `hasZ` (false on the Ray: definition `size.z` 0, so no Z axis) and `travel` (the model box ± `mcpTravelFudgeMm` at each end).
- `get_position` — the machine POSITION OF RECORD: judged machine coordinates with `reliability` (verified | heartbeat | cached-offset | awaiting-resync | stale), the frame it rests on and `reasons`, plus the raw work report and originOffset. Motion refuses unless verified/heartbeat/cached-offset; never derive machine = work − offset yourself. `connectedMachine: {identifier, type, hasZ}` says which machine you are driving — a Ray reports `hasZ: false` and machine Z 0 for ever; read it before planning, the laws differ by machine.
- `query_firmware_position` — raw `M114`; use when `get_position` looks suspect. Empty replies and transport failures are errors. On a SACP channel (Ray, Artisan, J1) the transport acknowledges a G-code with a result code only and never forwards reply text: the tool then returns `raw: null`, `acknowledged` (liveness) and the subscription-derived `heartbeat`, and does not call the connection dead.
- `query_firmware_configuration` — secondary read-only `M503 S` diagnostic of configuration currently in use, not necessarily EEPROM values. Prefer `M114` for fresh position. Refused with nothing sent on a SACP channel (no reply text on that transport).
- `recover_machine_connection` — automatically preserve a diagnostic snapshot, then verify the retained HTTP session with a status GET and restart heartbeat polling. Never sends `/connect`, changes credentials or initiates touchscreen pairing. Refuses missing/expired sessions; no raw-backend fallback. Re-read fresh position after recovery. HTTP only: on a SACP channel the heartbeat is a controller subscription the server cannot restart, and the refusal says so (reconnect through Luban).
- `get_mcp_diagnostics` — event-loop stalls and timing evidence for slow or aborted procedures; `connection` contains server/build identity, attempt/session IDs, worker lifecycle, poll/report ages, recent events and pre-recovery snapshots; `machinePosition` counts rejected heartbeats by reason (out-of-bounds, frame-flip, no-offset-yet), resyncs and disconnects.
- `get_job_timing` — where a job's time went, from its event log; works for running, done and failed jobs.

## G-code jobs

- `convert_thread_milling_gcode {gcode, source_controller?, tool_center_path: true, tool_length_applied: true, spindle_mode, spindle_power_percent?, chord_tolerance_mm?}` — OFFLINE import of internal/external Machining Doctor exports to explicit absolute Snapmaker G0/G1. Requires zero cutter compensation and work Z already referenced to the fitted cutter. Choose `power_percent` with integer percentage 1–100 for the standard head, or `cnc_200w_rpm` to retain 8000–18000 source RPM on the 200 W head. Never auto-selects the head or rescales feeds. Returns `gcode`, `changes`, `warnings`, `sourceSpindleRpm`, arc/full-circle/segment counts and `validation`; no connection, staging, origin write or motion. Review, then submit the converted text with `head_type: "cnc"`, `frame: "work"`. See [thread-milling guide](thread-milling.md) and [agent skill](../../../../../.agents/skills/cnc-thread-milling/SKILL.md).

- `validate_gcode {gcode | gcode_path | upload_id}` — static inspection: extents, spindle state, distance-mode hazards, and the FRAME the job declares (G53 own-line = machine, G54..G59.3 = work; inline `G53 G0` flagged - the firmware ignores it; G92 flagged). Free, run before submitting. Takes the program from exactly one of the three intakes below and returns its `identity` (SHA-256, bytes, line counts, first/last motion lines) and `source`. REFUSED (not warned): a program whose spindle is still on at the end — `M3`/`M4` never followed by `M5`, or an `M3` after the last `M5` — the signature of a truncated program; the refusal reports what was received so you can see where it stopped.
- **Large programs (#237).** A real CAM file (hundreds of KB, tens of thousands of lines) is never emitted as one `gcode` argument. Two intakes, both validated, frame-resolved and staged exactly like inline text, both capped at 4 MiB (`MAX_GCODE_PROGRAM_BYTES`, the server's request-body cap):
  - `gcode_path` — a file the **Luban server** reads from an allow-listed directory: Luban's own `<data dir>/mcp-jobs-inbox/` (always; `get_stored_state.jobIntake.inboxDir` gives the absolute path) plus one optional extra directory from Settings → MCP Server → Job files (`mcpJobInboxDir` / `LUBAN_MCP_JOB_INBOX_DIR`). Pass the name relative to the inbox or an absolute path inside it. Anything else is refused: paths outside the allowed directories, any `..` segment, a symlink or junction inside the inbox that resolves outside it, a directory, a missing file. Write the file, then one `submit_gcode_job {gcode_path, name, frame}` call stages it.
  - Chunked upload, for a client that cannot write to the server's filesystem: `begin_gcode_upload {name, total_bytes, sha256}` (UTF-8 byte count and hex SHA-256 of the WHOLE program as you will send it) → `append_gcode_chunk {upload_id, seq, text}` in seq order from 0, split on line boundaries, at most `chunk_max_bytes` (256 KiB) each — a repeat of a seq with identical content is a no-op (retry-safe), a different repeat or a gap is refused → `finish_gcode_upload {upload_id}` refuses until every declared byte arrived, verifies the SHA-256 (a mismatch discards the upload) and returns the identity. Then `validate_gcode {upload_id}` (leaves it in place) and `submit_gcode_job {upload_id, name, frame}` (consumes it on success; a frame refusal leaves it for one re-submit). Untouched uploads expire after 30 min; 8 may be open at once. Nothing is sent to the machine by any of these.
- `submit_gcode_job {gcode | gcode_path | upload_id, name, frame?: "machine"|"work", head_type?}` — stage a file job from exactly one intake (above); the confirm page carries a **Program identity** table (source, SHA-256, bytes, lines / motion lines, first and last motion line, last line, spindle state at end) and the result's `job.identity` / `job.source` say the same, so the operator can check the staged program against the file they generated before approving. Returns the confirm-page URL — deliver it to the operator as the last line of your message, alone. REFUSED unless the job declares its frame: `G53` on its own line before the first move (machine), or `G54..G59.3` in the file / `frame: "work"` for a Luban/slicer export (work; the file is never modified). `frame: "machine"` without a literal G53 is refused. The confirm page shows Frame and machine-resolved Z extents when resolvable. A file that selects only `G54` before its first move (converted thread-milling output) shows machine Z "if G54 is the active workspace" (`machineZResolvedFor: "G54"`); `start_gcode_job` then selects G54 with no motion and refuses to stream unless its offset Z matches staging. Other named workspace selectors, mixed frames and origin writes leave machine extents unresolved: one live offset cannot establish every section; review each required workspace separately.
- `start_gcode_job {job_id, wait_for_approval_ms?, wait_ms?, confirm_token?}` — after delivering the confirm URL and ending the staging turn, call with `wait_for_approval_ms` (e.g. 110000): the operator's click on the confirm page starts the job; `approved: false, timed_out: true` means call again, never restage. A file job with `machineZResolvedFor` first selects that workspace (no motion) and verifies its offset; a mismatch ends it `workspace-unverified` with nothing streamed - verify the workspace, then restage. Procedures return the result if it lands within `wait_ms` (default 25 s), else `running` — long-poll `get_gcode_job_status`. A procedure that fails within the wait carries its own `failure_recovery`; a file job's ends asynchronously, on the job record.
  File starts are observed before the HTTP request. A lost reply is reconciled for up to 6 seconds against fresh heartbeats from the same connection (file name must match when reported); a confirmed run receives normal progress, telemetry and completion tracking. If evidence is inconclusive, `start_unverified` remains active and monitored, including after the call returns. Idle alone cannot prove that a short file never ran. `retry_safe: false` means **do not retry or restage**: ask the operator to review and, if needed, use `stop_gcode_job`. Competing starts, pendant control and frame restoration remain blocked. Only an explicit refusal before dispatch reports `start_failed` with `retry_safe: true` (restaging still needs new approval). The job's `start_attempt` retains the transport error, request/observation times and latest status; the start result also exposes `machine_status_after`.
- `get_gcode_job_status {job_id, wait_ms?, since_event?}` — event log plus stored result and `ending` (why it ended: completed | stopped-by-agent | stopped-by-operator | withdrawn | rejected-by-operator | crash-alarm | overtravel-alarm | unexpected-contact | controller-rejected | workspace-unverified | timeout | operation-failure | machine-stopped | completion-unverified, with reason and measured count); a stopped or failed procedure keeps every completed station under `result`; `job.failure_recovery` reports a `G53`/`G91` the job may have left (see **Jobs** under motion). Long-poll with `wait_ms` / `since_event` instead of spinning.
- `stop_gcode_job` — procedures stop cooperatively at the next step and raise; file jobs get a firmware stop. Partial result kept.

## Transport and direct motion

- `home {ignore_stale_position?: boolean}` — machine home (`G53;G28;G54`; also homes B). Default first step after (re)connecting; raises Z first and clears the NOT-HOMED state. It is not a remedy for a `get_position` reliability of `awaiting-resync` or `stale` — a rejected or aged beat is a reporting fault, not a position fault, and motion is refused until the record recovers on its own (next coherent beat, ~2 s). On a Ray it sends GRBL `$H`, as Luban's Home button does for the Ray (its firmware never answers the SACP 0x01/0x35 home request); on other SACP channels (Artisan, J1) the channel's own home request is sent instead of `G53;G28;G54`. Either way completion is still verified from fresh beats (homed, idle, stable). A Ray homes to about X-1..1, Y399 (#260). `ignore_stale_position` bypasses only a `stale` position; when the channel has published no state yet it also waits a few seconds for the first report, because the idle and toolhead-off checks need one.
- `set_workspace_origin {workspace, origin_machine: {x,y,z}, datum_reference, reason}` — HUMAN-GATED replacement of all XYZ in an explicit G54–G59.3 workspace. Origin is measured machine coordinates, with Z as TOOLHEAD Z for the fitted tool. No motion or need to visit zero. Checks unchanged staging state, requires firmware selection acknowledgement and two fresh readbacks; no B/E write or automatic rollback. Leaves the named workspace active and invalidates earlier staged jobs. See [workspaces](workspaces.md).
- `select_workspace {workspace, reason}` — HUMAN-GATED selection/readback of an existing G54–G59.3 workspace without rewriting its origin. Prefer one WCS; additional workspaces only when necessary, particularly for existing G-code jobs. Standard MCP procedures may reselect G54, so verify/reselect before submitting the file.
- `goto_work_origin` — STAGE XY to work X0 Y0 at the current toolhead Z; no automatic raise, Z0 descent, datum setting or physical registration check. The confirm page shows the MACHINE destination; untrusted offsets, insufficient transport height, travel and mapped landmark conflicts are refused. Check the actual route and fitted tool/holder against fixtures. After B rotation, a retained WCS can remain valid while access to zero is obstructed; use another verified entry without re-zeroing. Distinct from `home`, which runs on the call. On a Z-less machine the height refusal does not apply and the step is relative, as `traverse_xy`.
- `move_z {z | z_targets[], coordinate_system: "machine"|"work", feed_rate?, reason}` — single Z target or a batch; one approval covers the list, one `start_gcode_job` per step. Each `z_targets` entry is a number or `{z, feed_rate?}` (#240): a per-step feed, so the standard fast-then-creep approach (`[{z: 191.5, feed_rate: 400}, {z: 181.5, feed_rate: 60}]`) is one job; a step without its own feed runs at the call's `feed_rate`; every feed is clamped to 50-600 and every clip is reported (`result.feed_clamps`, `; CLAMPED:` on the page); the page lists each step's feed and each step's gcode carries its own `F`. Only on the operator's explicit request. Refused outright on a machine with no Z axis (`connectedMachine.hasZ` false, the Ray): there is nothing to raise.
- `traverse_xy {x?, y? | targets: [{x?, y?}], coordinate_system?: "machine" (default) | "work", feed_rate?, reason}` — law-2 TRANSPORT: an absolute XY target or an ordered `targets` series at the height the head is already at (>= the motion floor), one approval, one `start_gcode_job` per leg, like `move_z`. Refused unless the head is already at/above `mcpMotionFloorZ` (default 320; no override); every leg checked against landmarks and the travel; Z never written; default frame machine (`G53` per step). **Top-Z policy (#241, setting `mcpTraverseWithoutApprovalAtSafeZ`, default on):** with the head already at/above `mcpSafeTraverseZ` (328) on a verified/heartbeat, homed position and the route checks passed, the call EXECUTES the series itself — `executed_without_approval: true`, job marked `approval.source: "policy"`, no confirm page; otherwise `staged_because` says why it staged. Use this, never a hand-written file job, to move the head. **Machine-aware (#260 follow-up):** results carry `connected_machine {identifier, type, hasZ}` and `travel.basis` (the machine model ± `mcpTravelFudgeMm`, e.g. `Ray model 600 x 400 + 25 mm fudge each end: X -25..625, Y -25..425`). On a machine with **no Z axis** (the Ray) none of the Z laws apply — no motion floor, no traverse height, no raise-first, and refusals never suggest `move_z` — the series runs at the machine's only height, it is always **staged** (the top-Z policy never auto-executes: there is no safe height to justify skipping the click; `staged_because` says so), and each step is a **relative** `G91 / G1 X.. Y.. F.. / G90` increment (`gcode_form` in the result), the form Luban's own Ray jog sends (`ControlPanel.tsx relativeMove`) and the one its firmware is known to execute: GRBL's `G53` is a same-block prefix, not the own-line `G53;` every MCP emitter uses for the Snapmaker 2.0, and neither form has been seen to work on the Ray's firmware, so no frame word is sent at all. Each relative step carries a `; mcp-settle machine X.. Y..` comment (stripped before sending) naming its absolute machine endpoint, which the runner verifies against the heartbeat before the next step; the confirm page's Frame row reads RELATIVE. A350 behaviour is unchanged: absolute `G53` steps, floor and top-Z policy as before.
- `move_and_capture` — one guarded XY move followed by a position-stamped frame; the unit of visual alignment. Z-gated first: the head is raised to the safe traverse height before any XY, and the call is refused when Z cannot be established. Not transport: for a top-height transit use `traverse_xy`. On a machine with no Z axis (`connected_machine.hasZ` false) the Z gate is skipped (`z_gate` says so) and the move is a relative `G91/G90` increment at the only height; the travel cap, pacing guard, idle/toolhead-off and route checks still apply, against the connected machine's landmarks only.
- `goto_tool_change_position` — ONE approval covering two exact steps (Z up, then XY to the operator-set park spot); call `start_gcode_job` once per step. With the head already at the park Z under the top-Z policy above, the Z step is skipped and the XY leg runs on the call after the landmark/travel checks. Refused on a Z-less machine (its first step is a Z move), as is `survey_bed` (it plans Z levels and hops).
- `move_z` — an UP-only series to no higher than the traverse height runs on the call under the same policy; anything that descends stages.

- **Failed calls (all tools)**: when a mutating tool fails after sending `G53`/`G91` (or a payload whose outcome is unknown) in its own async context, the registry may restore `G90`, then `G54` when `G53` is or may be active, as separate no-motion commands on the same connection (an unknown `G55`-`G59` selection is warned about, never reset). Sends a call launches in the background are detached and not its exposure. The error text keeps the original message first, then `failure_recovery: {status, skip_reason, commands, connection, resulting_modes, position, recovery_action, warnings}`; structured error results get a `failure_recovery` field, and so does a SUCCESSFUL mutating call that left `G53`/`G91`/an unknown mode (status `skipped`, nothing sent; not for a still-pending payload or under a running job). Cleanup is never sent after a stop, trip or overtravel, while a crash/overtravel latch or stop request is set, on a replaced connection, while the machine is not idle, or behind this call's own unanswered payloads, all re-checked before each send; a failed `restore_work_frame` is reported (`restore-tool-itself`) and nothing is ever retried. `workspace_verified` is true only when G54 was sent and the first reading after the settle is a status report stamped at least 2 s after the cleanup reply, judged work-frame, with a work offset above 0.5 mm, and impossible as a machine position (the `restore_work_frame` rule); otherwise the workspace reads consistent-unverified, unverifiable (offset ~0), still machine-frame, or no fresh beat. `position.trustworthy` needs a reliability that allows motion and either a `verified` echo (physically valid; the cleanup voided its record, so re-read `get_position`) or a proven frame. A cleanup holds the call about 4.5 s longer. `skipped`/`failed`/unverified evidence means: once no job is starting or running, call `restore_work_frame` and re-read `get_position`. An accepted `G90` never proves the distance mode - declare `G90`/`G91` in every program. The hook shares the USB pendant's frame-uncertainty latch: it never sends while the pendant holds the gcode lease or while the latch is already set (`another-operation-active`, nothing sent, no duplicate restore); whenever `G53` may be active and the cleanup was skipped, failed or not verified it raises that latch, so `get_position` shows `FRAME UNCERTAIN`, `requireReliableMachine` refuses motion and pendant arming is refused until `restore_work_frame` (or the pendant's Restore) is accepted AND a verified position follows; `position.frame_uncertain` carries the latch and `position.trustworthy` is false while it stands. `feed_override` reports the last accepted `M220 S<n>` (sent by pendant runs), which persists on the controller.
- **Jobs (`start_gcode_job`, `stop_gcode_job`, `get_gcode_job_status`)**: a job that may have left `G53`/`G91` carries `job.failure_recovery` (also top-level on `stop_gcode_job` and on a procedure result or error inside the start wait). Procedure runners are judged on their own ledger when they end, like a failed call. File jobs are judged from the program text: after a stop every line from the last `currentLine` seen (less a 16-line margin) to the end of the file may have been parsed, so their modes may read `unknown` (`exposure.file_window` says which lines). A file job is never cleaned up automatically: stop, trip, lost connection and completion all report `skipped` with `restore_work_frame`; a completion that left `G53`/`G91` is `job-completed-with-modal-exposure`.
- `restore_work_frame {reason?}` — `G90` + `G54` on their own lines, NO MOTION. The cure for a controller left in the machine workspace by a job that declared `G53` and never handed the frame back: every beat then carries machine coordinates with the work-origin offset still populated, `raw − offset` is impossible, and the position of record refuses everything - including this, which is why it is explicitly allowed while `awaiting-resync` or `stale`. Reports the position before and after (`before`/`after`, `frame_before`/`frame_after`) and `workspace_verification`, judged from the first reading after a two-beat settle with the same rule as the failed-call cleanup: `verified` (a beat stamped at least 2 s after the reply reads as work-frame, the work offset exceeds 0.5 mm, and the raw report is impossible as a machine position), `consistent-unverified` (work-frame, but the raw report would also be a legal machine position: compare `query_firmware_position` with `get_position`), `unverifiable-zero-offset` (offset 0.5 mm or less on every axis, both frames read alike), `no-fresh-beat` (nothing judged after the reply yet, an incoherent or stale beat: wait 2 s and re-read `get_position`) or `machine-frame` (still in G53: do not move, check the frame with `query_firmware_position`, tell the operator). `recovered` is true only for `verified` with a usable position; it no longer compares reliability before and after, because a sustained machine-frame state already reads as `heartbeat`. `note` names the next step. Refused with nothing sent while an MCP job is `starting` or `started` (the error names the job): wait for it to end or `stop_gcode_job` first. A re-home is not the remedy.

## Camera and vision

- `list_cameras` — enumerate capture devices (DirectShow names on Windows, `/dev/v4l/by-id` on Linux), plus `selection` (which camera captures actually use: `url`, `device`, `last_good`, `effective`, `pinned`) and `stream` — `enabled`, `stream_url` (`/camera` page for the OPERATOR's browser; not for the agent to fetch), `running`, `clients`, `fps`.
- `preview_cameras {device?}` — one frame from EACH attached camera (or just the named one), labelled with its device string and `frame_id`. With two cameras attached both return good-looking frames and nothing downstream can tell which is which — the measurements are simply wrong — so look before you pin. A camera that will not open is reported beside the others, never substituted. Read-only; the selection is untouched.
- `select_camera {device | clear, confirm_frame_id?, operator_confirmed?, reason?}` — pin which camera every capture uses (`mcpCameraDevice`, or `mcpCameraUrl` for an http(s) snapshot URL — picking one clears the other, since the URL wins wherever both are set). `device` matches a `list_cameras` entry, its `/dev` path (symlink or the node it resolves to), or its friendly name; ambiguous matches and bare indices are refused, never guessed. `confirm_frame_id` must be a frame that came from THAT camera (from `preview_cameras`) — waived only when one camera is attached or the selection is unchanged; `operator_confirmed` is the OPERATOR's word, not the model's. Returns a fresh frame from the camera it just selected, restarts the live stream loop onto it, and — when the camera actually changed — marks the solved camera model unverified, because that geometry belonged to the old camera. `clear: true` unpins.
- `capture_frame` — position-stamped frame with a `frameId`, the expected tool region, nearby landmarks, `source` (`stream` = served by the live MJPEG loop someone is watching, `one-shot` = this call opened the device) and `stream_url`. Every requested snapshot is archived under `mcp-camera-captures`; the last 12 also stay in RAM. Returned `camera.file` and `frameId` remain usable after cache eviction and restart. Works the same whether or not the stream is running.
- `get_frame {frame_id | file}` — any requested snapshot by ID (RAM then disk), or a saved image/mosaic inside MCP camera-capture, program-frame, bootstrap or survey directories. **There is no 12-frame retrieval or survey-size limit**; 12 is only the RAM cache size. JPEG and PNG responses carry their actual MIME type. Server paths are accepted from remote clients; extensions and real paths are constrained. Read-only, no capture/motion.
Requested snapshots are retained until their archive files are explicitly removed; there is no automatic age/count eviction on disk. Continuous live-video frames are not archived. Frames already lost from the old RAM-only cache cannot be recovered. Survey/programme images have their own saved paths and indexes.

- `get_camera_capture_set {directory}` — read the position-stamped `index.json` from a bootstrap/survey result directory. Returns targets, frames, holdout flags, physical plane and mosaic metadata as recorded. Fetch images with `get_frame`; save the index and images by basename to run the offline solver locally. No SSH/server filesystem access needed.
- `camera_program {name, reason, ops}` — one staged procedure with 1–80 ordered `{id, kind, ...fields}` ops. The live `ops.items.oneOf` schema defines all fields and rejects unknown fields/references before staging. Kinds: `move_z {machine_z}`, `survey_bed` (standalone fields, no mosaic), `move_and_capture {x,y,machine_z}`, `capture`, `track_feature {template_capture_id,search_capture_id,point:{u,v}}`, `fit_calibration {samples:[{track_id,dx_mm,dy_mm}],max_residual_px?,valid_at_y?,z?,surface?,notes?}`, `verify_calibration {fit_id|jacobian+matrix,tolerance?}`. Tracking uses a 41 px patch and 120 px search. Fit stores a local 2×2 inverse (5 px residual limit default), not the camera model; verification checks M·J only (0.25 default). `operator_confirmed_clearance` is permitted only on specifically cleared survey/move-and-capture ops, never at program level. Result `ops` is keyed by id, with saved `file`/machine positions, tracks, matrices/residuals/store entries; failures retain completed ops and retreat/HOLD outcome. Initial anchor/tool/obstacles/model are rechecked before execution. Deliver the URL last, end the turn, then `start_gcode_job`.
- `set_tool_region` — tell the server where the tool appears in frame so captures can flag it.
- `track_feature` — normalised cross-correlation of a template between two captured frames (RAM or disk). Use instead of eyeballing pixels.
- `set_camera_calibration` — Y/Z-keyed pixel-to-mm calibration, optional `surface` depth tag and `jacobian`. Sign-flipped matrices are rejected. Tagged with the connected machine; `visual_servo` and the nearest-Y lookup use only the connected machine's entries (untagged legacy entries are the A350's); each entry reports `machineScope`.
- `get_camera_calibration` / `delete_camera_calibration` — read or remove a stored calibration.
- `visual_servo` — one clamped step toward a seen target per call. Trips when the error stops shrinking or the response diverges from the calibration prediction (parallax signature).
- `survey_bed` — approved serpentine XY camera grid at gantry height; whole-bed mosaic for finding stock and fixtures. New: `overlap_fraction` + `plane_z` derive the pitch from the camera model's real field of view ("seamless" is a relationship between pitch and field of view, and a picked pitch is not one); `z_levels` runs the grid at several heights under ONE approval, each entered with XY stationary; with a verified model each pass is composed into `mosaic_z<Z>.jpg` indexed in machine coordinates, and the seams double as a drift check that marks the model unverified when overlapping frames disagree.
- *(not a tool)* Live view for humans: `GET /camera` on the MCP port (`stream_url` above) — MJPEG at `/camera/stream.mjpeg`, one JPEG at `/camera/snapshot.jpg`, `/camera/status.json`. Same LAN gate as `/mcp`; off (Settings → MCP Server → Camera) = 404.
- *(not a tool)* Browser trust for the HTTPS listener: `GET /trust` (per-OS install steps) and `GET /ca.crt` (the public mkcert CA) on the plain HTTP port, linked from the job dashboard and Settings → MCP Server once HTTPS is configured. Hand the `/trust` link to an operator whose browser refuses the HTTPS confirm/dashboard pages or their system notifications; the key is never served.

### The camera model (the camera is SESSION STATE, not a rig constant)

`survey_bed.machine_z` is TOOLHEAD machine Z, asserted before XY, mutually exclusive with
`z_levels`. Active tools do not bypass the floor. A legacy Z328 box still excludes Z320 views
inside it: inspect dropped/clipped coverage and use park height when necessary. `plane_z` is
PHYSICAL surface Z at the applicable B, never the toolhead height. `bed_plane_z` is used when
stored; without either, zero is an unmeasured placeholder for qualitative frames only and no
metric mosaic is rendered. Overlap requires an explicit/stored plane and a verified model;
spacing is chosen to satisfy every requested height. Seam mismatch invalidates metric use but
does not distinguish camera drift from wrong plane, parallax or poor matches. Re-verify a known
target before re-solving; do not infer a replacement plane from a seam residual.

It can sit differently after every power cycle, be knocked, be re-aimed, or be a different camera. Nothing converts a pixel into a machine coordinate, or a machine coordinate into a pose, until a model is solved AND verified on this connection. Plain captures never need one.

- `get_camera_model {history?}` — the model, its state (verified | unverified | superseded), why it is not usable, and which tool fixes it. Read-only.
- `verify_camera_model {target, pixel_u, pixel_v, tolerance_px?}` — predict where a target of known machine coordinates should appear at the CURRENT toolhead position, compare with where it does, record the residual in px and mm. **Before metric camera use; plain observation needs no calibration.** Beyond tolerance the model stays unverified and says the camera has probably moved. No motion - position with `traverse_xy` first.
- `camera_bootstrap {stage, reason, ...}` — solve the geometry FROM NOTHING, two staged procedures, one approval each. `stage: "search"`: a grid at the park height bracketing the tool setter, whose machine XY is known exactly - which frames contain it gives the camera offset INCLUDING ITS SIGN with no prior assumption, and it is the only step meaningful without a calibration. `stage: "poses"`: the poses that implies, each sweeping Z from the park height to the motion floor with XY stationary. A pose the TOOLHEAD cannot reach is dropped with a reason, never quietly adjusted.
- `set_camera_model {offset, rotation, intrinsics, valid_band_z, central_region, residuals, ...}` — store a solve from `scripts/camera_bootstrap.py`. Always stored UNVERIFIED; the previous model is kept superseded, never overwritten.
- `plan_view_pose {target, toolhead_z?}` — where must the TOOLHEAD go to see this machine point? Returns the pose, the standoff and the field of view, from the model. Use it instead of computing a pose; never carry one between sessions.

Bootstrap poses accept `holdout: true`: choose distinct XY from observed search frames, not
`plan_view_pose` while the model is unverified. Holdouts run last and the solver excludes all
their frames. Poses finish at park Z above the last pose; `result.finalMachine` reports it.
Take a fresh verification capture there after `set_camera_model` (default 8 px threshold).
Review dropped/restricted poses; at least two useful fit poses plus a holdout must survive,
and the solve still needs sufficient independent geometry. Search `y_span_mm` defaults to 0;
widen it when the viewing direction is unknown. Each moving bootstrap stage returns its own
confirm URL. The solve, model store and verification themselves have no confirm page or motion.

## Landmarks and scene

- `set_landmark` — name a scene feature by machine extent, optionally with `clearance_z`. Landmarks are obstacles: planners refuse XY paths that cross them below clearance. **Machine-scoped:** each record is tagged with the connected (else Luban-selected) machine's identifier and applies to that machine only — the A350's rotary keep-out (X140–200) means nothing on a Ray. Records written before 2026-10-18 carry no tag and are the **Snapmaker 2.0 A350**'s by rule (the only machine the MCP ever ran on before then): they keep applying on the A350 exactly as before and stop applying on the Ray. `get_stored_state` shows each record's `machineScope` (`machineIdentifier`, `legacy`, `appliesToConnectedMachine`). The same name may exist once per machine.
- `delete_landmark` — remove one.
- `set_probe_geometry travel_*` — the stated travel is machine-scoped too (`mcpTravelMachine` names the machine; untagged values are the A350's) and only ever **tightens** the machine model plus the travel fudge for that machine; a looser statement is reported in `travel.conflicts` and ignored. Stating any end for a different machine retires the previous machine's ends. The fudge itself — the allowed range per axis is `[0 − fudge, size + fudge]` — is `mcpTravelFudgeMm` (configstore) / `LUBAN_MCP_TRAVEL_FUDGE_MM` (env, wins), default **25 mm**, with optional per-axis `mcpTravelFudgeXMm` / `mcpTravelFudgeYMm` (`LUBAN_MCP_TRAVEL_FUDGE_X_MM` / `_Y_MM`). 25 covers the A350's real X−19..339 / Y342 against its 320 × 350 definition and the Ray's home at about X−1 / Y399 against 600 × 400, and still refuses X650 on the Ray. The position judge's bounds use the same model-plus-fudge box (its own 50 mm garbage margin on top); a Z-less machine has no Z range check at all.

## Enclosure (no motion, no confirm page)

- `get_enclosure_status` — `present` (the machine reports the enclosure module online), `light_percent`, `fan_percent`, `door_detection` (SACP: `door_detection_by_head`), `door_open` (serial only), `source` and a `reason` when absent. Read-only; the same enclosure query Luban already polls.
- `set_enclosure_light {percent 0-100 | state "on"|"off"}` / `set_enclosure_fan {…}` — LED strip / exhaust fan through the same channel call as the Workspace enclosure widget (SSTP `/api/v1/enclosure`, SACP EnclosureInfo, serial `M1010`), never a hand-typed M-code. Runs on the call (no motion). Refused when not connected or when `present` is false. Returns `requested_percent`, `reported_percent`, `readback_matches` and the status `before`/`after`; a stale readback catches up on the next report — re-read, do not resend. The Snapmaker 2.0 enclosure drives both at 0 or 100.

## Probe feed (external sensors: tool setter, overtravel switch, touch probe)

- `get_probe_feed_status` — transport, per-channel last readings, tripwire state.
- `connect_probe_feed` — bring up the MQTT or Blinka GPIO feed; connecting arms the overtravel tripwire.
- `disconnect_probe_feed` — drop the feed.
- `clear_overtravel_alarm` — reset a latched overtravel trip. Operator's explicit word only.

## Tool setter and tool change

- `set_active_tool {protrusion_mm, protrusion_reference?, source, note?, tool_identity?, measurement_job_id?}` — records fitting evidence without motion. `protrusion_reference:"toolhead"` requires an explicit conservative distance below the machine toolhead reference. Omitted, `collet` or `unknown` references do not authorize physical clearance. Measured sources must match the current completed setter measurement and verified bound. Legacy toolhead boxes and the camera motion floor remain enforced.
- `get_active_tool` — current assertion and its clearance basis, or `active:null` with historical evidence and stale reason. Restart, disconnect/reboot and tool-change parking invalidate it; do not blindly replay an old fitting.
- `set_tool_setter_config` — approach reference/centre, optional named `setter_datum {id,name,machine_z,basis,source,uncertainty_mm?}` and optional independent `toolhead_clearance_bound {mm,source}` conservative maximum. Measured datum basis requires uncertainty. Nominal reference and longest lengths plan approach only. Datum omission preserves the existing convention; clearing the independent bound requires explicit null.
- `get_tool_setter_config` — config, named datum, raw measurement history and active fitting. Missing historical datum/fitting provenance remains unknown.
- `run_tool_setter {bit_length_mm, tool_identity?, fitting_id?, ...}` — one approved sensor-gated measurement with raw trigger, confirmation contacts, job/date and datum snapshot. `bit_length_mm` is an approach-only estimate in the configured nominal reference convention, not arbitrary collet protrusion. `store_as_reference` updates approach reference without changing the established datum. `accept_probe_contact:true` identifies a spindle-probe measurement. Successful finish raises to traverse height; `stay_at_trigger` / `start_from_current` support the manual swap wizard.
- `apply_tool_length_offset` — confirmed `G92` transferring work Z by new-minus-old raw setter trigger. Requires the applicable measurement pair; a shared datum cancels.

Contact/procedure results retain raw toolhead coordinates and add `tipMachineZ` plus the captured
`tipCalibration`. A conventional projection is labelled; unavailable calibration yields null.
These fields never retrofit today's datum onto historical surveys or alter work coordinates.

## Touch-probe procedures (staged, one approval per circuit, results in machine coordinates)

- `probe_point` — one axis from the current position. The atom.
- `probe_vector` — probe along any downward or lateral unit vector.
- `probe_approach_and_hold` — the datum hold (#188): raise if below the traverse height, hop there to `x/y`, guarded descent to `start_z_machine`, sensor-gated march along `dx/dy/dz` (default −Z), then HOLD for the operator's touchscreen work-origin setup — in contact at the confirmed datum, backed off `backoff_mm` (`hold_at`), or at a stated `datum_z_machine` reached without contact; `on_contact: "abort"` makes any touch an `unexpected-contact` ending. The job stays `started` with `job.hold` (held position, measured contact, sensor, handoff text); `stop_gcode_job` is the sanctioned raise (release along the vector, then straight up) and keeps the measurement in `result`. Requires the probe feed armed at staging; takes the stylus-reach arguments.
- `probe_sequence` — enumerated hop / descend / probe circuit. By default every probe returns to its own start and raises, including continuing misses; keep-out boxes honoured at plan time. A `descend` step may state `descent_segment_mm` (default 5, 1-5, #166): the longest fast segment of that descent under the crash guard, for a column not proven clear; the page states the length used, a value above the cap is clamped and reported. Opt-in `local_links: {clearance_z, max_hop_mm?}` (#242) links stations at a stated toolhead machine Z above the measured top (hops ≤ 60 mm, checked against landmarks/keep-outs at that height, enumerated on the page; first hop and final exit at the traverse height). Use a continuous procedure below for related local stations whose geometry fits.
- `probe_circle` — N radial marches plus least-squares circle fit. Inside a hole, returns to the staged interior origin between radials; outside a boss, repositions at full height. Reports rms and residuals.
- `probe_surface_path` — N minus-Z stations along a line: per-station contact, best-fit slope, flatness. Optional `capture: {stations: [1, 4], settle_ms?, label?}` saves stationary photos at selected contacts before retraction (also `probe_surface_grid`).
- `probe_surface_grid` — serpentine minus-Z grid: Z matrix, best-fit plane and residuals, ASCII height map. Both scans link locally: guarded at last contact plus `z_safe_delta_mm`, stepped at last contact plus `hop_lift_mm` with contact recovery. Both take `descent_segment_mm` (default 5, 1-5, #166) for the approach to station 1.
- `probe_stock_outline` — from a block estimate, find its top, outline and centre. Links top samples and same-side samples locally; raises when changing sides.
- `probe_wall_follow` — repeated vertical-wall contacts with standoff and stepped links away from the face on a bump; no full-height return between stations.
- `probe_corner` — internal corner between fitted walls: bisector find then radial probes from the measured centre, returning there between contacts.
- `probe_trace_perimeter` — bounded internal-pocket crawl with release-verified standoff, coarse steps on proven straights and selective confirmations; external tracing is not exposed.
- `probe_program` — composite program: an ordered list of operations, derived references, jig geometry, keep-out and groups under one approval. The new-stock survey lives here. Each completed probing op ends raised; references/groups do not fuse local motion between ops. Op kinds: `rotate_b`, `surface_path`, `surface_grid`, `sequence`, `stock_outline`, `wall_follow`, `corner`, `trace`, `capture {x?, y?, z?, descent_segment_mm?}` (a position- and B-stamped frame saved on the job record; with x/y it first hops there at the traverse height, travel- and obstacle-checked like a sequence hop; with `z` - a measured or operator-stated toolhead machine Z, or a bounded reference to an earlier top touch, never a guess (#177) - it then descends to it as a sequence descend step does (fast segments to 20 mm above, then 1 mm sensor-checked steps, any contact aborts the program), settles, frames at that Z and raises straight back to the traverse height, the column checked against landmarks and keep-outs at staging and again live; with neither, no motion) and `home` (machine home, last op only, homes B too) — so "capture at (x, y), rotate_b 180, capture, home" is one click.
- `set_probe_geometry` — jig and tool constants a rotary `probe_program` can reference as the `axis` namespace. Measured or operator-stated, with a reason. The rotary axis is a line: `rotary_axis_point` / `rotary_axis_points` record the measured `(x, z_physical)` at two or more Y stations (source and date each); yaw, pitch and the axis at any Y derive from them, and the legacy `rotary_axis_x` / `rotary_axis_z_physical` become the line's values at its reference Y. `probe_stylus_exposed_mm` (tip bottom to the first body shoulder) is the stylus REACH `get_stored_state.geometry.stylus.reachMm` — not the probe's tool length. Every −Z / in-pocket planner (`probe_point`, `probe_vector`, `probe_sequence`, surface scans, `probe_circle`, `probe_corner`, `probe_wall_follow`, `probe_trace_perimeter`, `probe_approach_and_hold`) takes `rim_z_machine` (alias `surface_z_machine`, the toolhead Z at which the tip touches the rim the body would land on) and `reach_margin_mm` (default 2); with a stored reach the plan is refused at staging when its deepest commanded Z lies more than reach − ball − margin below that rim, with the numbers; with no stored reach the result and confirm page say "stylus reach unknown: body collision not checked" (issue #187).

`probe_program {dry_run:true,...}` validates the same plan and returns `eventBudget`,
`jobEventLimit`, `fitsEventLimit` and a recommended limit without staging or motion. Normal
staging refuses an oversized budget. Surface ops budget 40 + 120/station plus other op/program
overhead; use measured timing for runtime, not that count. `set_probe_geometry` also stores
`probe_stylus_exposed_mm`, `probe_body_diameter_mm` (references `probe.stylus_exposed_mm` and
`probe.body_diameter_mm`, null refuses bounded references) and measured physical `bed_plane_z`.
Both tailstock and chuck-jaw keep-out volumes need current measured/operator-stated extents;
axis-centre points alone cannot generate safe fixture boxes.

## CAM probing programs

- FreeCAD side: `docs/post/freecad_probe_emitter.py` writes a `run_probing_gcode` program with `(PROBE ...)` nominals, normals and tolerances read straight off the selected faces (the Path Probe operation carries none of that, so it is bypassed, along with the post processor). `frame="machine"` + a measured `App.Placement` for a re-clamped part.

- `run_probing_gcode` — stage a CAM-generated probing program (Fusion 360, FreeCAD, any Grbl/Marlin post, or hand-written). `G38` cycles are translated into staged probes, never sent raw. Default `link_mode: raise` repositions at full height; `stepped`/`wall` provide local links with blocked-station handling. Every G38.2/G38.3 cycle still returns to its own start. Returns an inspection report.
- `get_inspection_report` — re-render a finished/aborted **run_probing_gcode** CAM report. For probe_program, probe_sequence and surface scans, read `get_gcode_job_status.result`; unsupported report requests return that pointer.

## Accelerometers (no motion; captures write files and calibration changes stored state)

See the README's "Accelerometers" and the `cnc-vibration` skill.

None of these moves anything. Motion a diagnosis needs is staged with the ordinary tools.

- `get_vibration_status {live_s?}` — the feed (transport, each link - the Blinka bridge or each serial board - with its state, bridge, bus load; resource leases; what stops it), each sensor (id, `location`, chip, address/mux, rate, `orientation`, streaming state, measured rate, FIFO overruns, errors), bus load, the stored rotary calibration, captures recording now; `live_s` adds a quick level / tone / gravity look at the last seconds.
- `capture_vibration {sensors?, duration_s?, lookback_s?, label?, wait?, ...analysis}` — record a window (optionally reaching back into the ring) and return the per-sensor report: acceleration RMS per axis and octave band, velocity RMS (ISO 10816 band), displacement RMS (band stated), tones with direction (`axis_share`, machine axes with an orientation) and amplitude, gravity with its tilt resolution. Waits up to 60 s by default; longer captures return a `capture_id` at once.
- `get_vibration_capture {capture_id, wait_ms?, sensor?, from_s?, to_s?, ...analysis}` — analyse a capture (also from earlier sessions: raw float32 samples stay on disk), over a sub-window (`from_s`/`to_s`: seconds from the capture's window start, outage-safe) or at another resolution. Analysis arguments, shared with `capture_vibration`: `resolution_hz`, `max_peaks`, `min_prominence_db`; rotation `rpm_hint` (0.80-1.05 x S) or `rpm_min`/`rpm_max`, `flutes` → `rotation` (RPM, confidence, `locked`, harmonics, non-harmonic peaks = chatter candidates); `motion {axis, feed_mm_min, targets?, bin_mm?, references_mm?}` → tones as wavelengths (mm/cycle) and orders against named lengths, movement segments, and with `targets` a position profile per direction (segments and legs must match one-to-one); `baseline_capture_id` + `lever_mm` → tilt change with resolution and significance, lateral displacement at the lever (tilt x lever), level change; `spectrum_points`.
- `stop_vibration_capture {capture_id, reason?}` — end a recording capture now (recording only).
- `list_vibration_captures {limit?}` — newest first, with window, job, sensors, controller B at start/end, directory.
- `measure_rotary_angle {sensor?, duration_s?, label?}` — still reading of the `rotary-chuck` sensor: gravity, stillness, controller B at start/end; with a calibration `absolute_b_deg`, `uncertainty_deg`, `trust_problems` (moved mount, tilted module) and `controller_minus_absolute_deg` (what a power cycle lost). Never rotates B or writes the controller's count.
- `calibrate_rotary_accelerometer {readings: [{capture_id, b_deg?}], sensor?, reason, clear?}` — fit and store the chuck sensor's calibration from >= 4 still readings spread over >= 180 deg of controller B in ONE power session (axis in the sensor frame, in-plane offset, rotation sense, angle at B0; residual reported). Refuses moving or non-still readings and an undetermined rotation sense. The caller must establish an unchanged power session, B datum and mounting and record provenance in `reason`; the tool does not enforce session identity. `clear: true` removes it.

## Standing rules the tools assume

- A tool or probe is always in the spindle; establish which is fitted and never plan as if the collet is empty.
- XY transport over 1 mm is planned at or above the motion floor, machine Z320 by default; park/procedure traverse height is machine Z328. Read the stored limits and canonical motion rules. Landmarks are honoured literally: a hop at 328 clears them on its own merits, a lower hop is checked like any low segment. **On a machine with no Z axis (`connectedMachine.hasZ` false — the Ray) none of this applies**: XY runs at the only height, every transport is staged for the click, `move_z` is refused, and only the landmarks, calibrations and stated travel set on THAT machine count.
- The XY travel is the connected machine's model size plus `mcpTravelFudgeMm` (default 25 mm) at each end of each axis; an operator statement can only tighten it for the machine it was stated on. Read `get_position.connectedMachine` first: the laws differ by machine.
- No Z motion without a direct request. "Home" always means machine home.
- Approval covers one bounded series of moves and never carries forward. A staged procedure or program is ONE approval for every move inside its envelope — the efficient lawful form.
- For staged motion, deliver the confirm URL as the last line and end the turn before waiting with `start_gcode_job`. `home` and `move_and_capture` are direct-call exceptions governed by `cnc-motion-rules`; never infer permission from this tool index.
- Agents plan, stage, record and quote in MACHINE coordinates. Every staged job declares its frame or is refused; `G90`/`G91` is distance mode, not a frame; never a bare frameless `Z`.
- The work origin is the operator's (touchscreen, Luban, tool-change wizard). Read it fresh from `get_position`; never assume it; write measured XYZ only through human-gated `set_workspace_origin`, or transfer measured tool length through `apply_tool_length_offset`. Prefer one WCS; multiple workspaces are frowned upon but supported if an existing G-code job requires them.
- `get_position.machine` is the judged position of record with a `reliability`; a reading more than 50 mm outside the travel is a bug, never a position, and is ignored until the next coherent beat. Do not derive a machine position from one heartbeat by hand.
- Canonical agent guidance: `.agents/skills/cnc-motion-rules/SKILL.md`.

### Probe-spot photographs and shoulder recovery

Sequence probe steps accept `capture: {settle_ms?, label?}`; surface scans select 1-based
`capture.stations`. Frames are saved beside measurement results before retraction. Continuous
viewing remains available at `list_cameras.stream.stream_url`; it does not synchronize a photo
to a contact. Stepped surface links use bounded ball-radius backoff along verified incoming
paths and sensor-check their rises. Nested probe holds stop the whole program, including
`on_fail: skip`. See [probe inspection](probe-inspection.md) for schemas, limits and recovery details.

`home.ignore_stale_position` defaults to false. Set true only on an explicit operator demand to home despite stale data. It does not waive alarms, idle/toolhead checks, incoherent positions or fresh completion verification.
