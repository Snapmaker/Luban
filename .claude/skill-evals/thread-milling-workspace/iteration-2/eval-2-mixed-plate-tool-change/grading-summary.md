## Most important observations about the skills/docs

1. **The "fixture is diagnostic only, not a recipe" instruction is stated in the prompt but not reinforced anywhere close to the conversion call itself.** `setup.md` explains the fixture's `CUTTER DIAM=1.38` / `L=2.25` traps at the diagnostic level, but nothing in `cnc-thread-milling/SKILL.md` or `setup.md` says, at the point of building the real `convert_thread_milling_gcode` argument list, "never carry a numeric value (OD, effective length, feed) forward from a diagnosed fixture into a real conversion call unless the operator has independently confirmed it for the real cutter." This is exactly the gap haiku fell through this iteration (assertion 5): it correctly recited the diagnostic finding in its own Findings section, then silently reused the same number a few steps later where the docs no longer had eyes on it.
2. **There is still no stated decision rule -- or explicit "there is no safe default here" -- for single- vs triple-row cutter selection**, and iteration-1's grading-summary already flagged this as qualitative-only guidance. This iteration shows the risk concretely: opus reasoned qualitatively without a hard number (correct), sonnet declined to reason at all (safe but incomplete), and haiku manufactured a specific numeric cutoff to fill the gap (unsafe). A line in `setup.md`'s cutter-choice paragraph saying "there is no documented threshold for this choice; state qualitative tradeoffs and gate the concrete choice on operator-confirmed cutting length, never invent a numeric cutoff" would likely have prevented haiku's fabrication while still letting opus's style of answer through.
3. **The tool-setter fabrication trap (special check (a)) and the README head-type trap (special check (b)) both appear fixed** relative to iteration 1 across all three models on this eval -- consistent with the skills having had explicit edits since iteration 1 (per iteration-1's own suggested edits to `cnc-probing/SKILL.md` and `tool-change/SKILL.md`). This is a good sign that skill text changes are propagating into planner behavior for the exact failure modes previously observed.
4. **Approval-count accounting is still fragile**, as flagged in iteration 1's observation #4, and this run shows it is now actively producing *false* self-reports rather than merely inconsistent ones: sonnet's plan states a literal tag count that is wrong by 4, and haiku's stated total is wrong by 2 due to a double-counted bucket. Both plans are internally auditable (their steps can be re-counted from the document), which is good, but neither model's own arithmetic can currently be trusted at face value.

## Concrete edit suggestions

1. **`cnc-thread-milling/references/setup.md`, right after the fixture-traps discussion** -- add: "A number identified as a fixture artifact (path radius, neck-vs-OD conflation, axial step) must not reappear anywhere in a real `convert_thread_milling_gcode` call for the operator's actual cutter. If the operator has not independently confirmed a cutting OD or effective length, leave that field pending and ask -- do not carry the fixture's number forward as a placeholder." This targets haiku's assertion-5 failure directly.
2. **`cnc-thread-milling/references/setup.md`, cutter-choice paragraph (single- vs triple-row)** -- add an explicit disclaimer: "There is no documented numeric threshold (cutting length, turn count, etc.) for choosing between single- and multi-row cutters. State the qualitative tradeoffs (turns/engagement vs. radial load) and gate the concrete choice on operator-confirmed dimensions; never invent a cutoff figure." This targets haiku's fabricated 4.5 mm threshold and would also nudge sonnet toward giving qualitative reasoning instead of declining to reason at all.
3. **RUN_INSTRUCTIONS.md or GRADER_INSTRUCTIONS.md, Counts line format** -- ask agents to literally enumerate or programmatically state the arithmetic for repeated steps (e.g. "6 file jobs x 1 approval each = 6," listing each hole's step number) rather than folding repeats into prose ("repeat once per M2.5 hole"). This is the direct cause of both sonnet's and haiku's wrong self-reported literal-tag counts in this run, mirroring iteration 1's observation #4 almost exactly -- the previous suggestion (from iteration 1) does not yet appear to have been acted on.
4. **evals.json, eval id 2, assertion 1** -- consider splitting into two: (a) "uses per-feature datums and one job per hole, no concatenation" (a practice check, satisfied by all three runs here) and (b) "explicitly names the reposition-and-replay failure mode and explains why it doesn't relocate the cut" (a genuine understanding check that only opus clearly satisfies). As currently worded, a plan that never even considers the invalid shortcut can pass on the weaker practice-only reading, which somewhat understates the discriminating power the assertion was clearly designed to have (per iteration 1's observation #1 about this exact eval).
