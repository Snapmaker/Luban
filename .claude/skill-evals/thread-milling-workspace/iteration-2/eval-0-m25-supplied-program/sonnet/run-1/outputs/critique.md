# Critique

## What helped

- `cnc-thread-milling/references/setup.md` names this exact fixture and cutter description ("1.38 mm neck... three axial rows") as a known trap: the file's toolpath assumes 1.38 mm is the *cutting* diameter, and the neck figure must not be accepted as evidence the cutter matches. This is close to a direct hit on the operator's phrasing ("1.38mm neck ... triple row threads, triple flute"), so the mismatch was easy to spot once the reference had been read — it would have been very easy to miss without it, since the fixture's own file header also says `CUTTER DIAM=1.38`, which superficially "confirms" the operator's number.
- `cnc-motion-rules` SKILL.md's law 7 ("ask once") and its explicit list of what to batch made it straightforward to combine the cutter-geometry questions with the orthogonal tool-change and head-identity questions into one message instead of drip-feeding them.
- `docs/thread-milling.md` and `TOOLS.md` cross-confirm the setup.md guidance almost verbatim (same 2×0.575+1.38=2.53 arithmetic, same 2.25 mm vs ~1.35 mm mismatch), so there was good redundancy for catching this rather than relying on one file.
- The canonical call shapes in `cnc-motion-rules` §8 and `tool-change` SKILL.md's step-by-step flow A made the conditional tool-change steps mechanical to write out correctly (protrusion vs diameter, park is one approval with two `start_gcode_job` legs, etc.).

## What was missing, unclear or contradictory

- It's not fully explicit whether `convert_thread_milling_gcode` (offline, no motion) is *itself* gated on `tool_length_applied` being physically true at call time, or whether the declaration is a forward-looking claim about the state that will exist once the cutter is loaded and the origin transferred. `cnc-thread-milling` SKILL.md says "Verify... work Z referenced to the fitted tool tip before making the two required declarations," which reads as a hard gate, but the tool call itself has no connection to the machine to check this — I resolved it conservatively (don't call `convert_thread_milling_gcode` with `tool_length_applied: true` until the tool-change is done or the origin history is confirmed), but a less conservative reading (call it for review purposes once the *plan* to satisfy the precondition is set) seems equally defensible and would change step ordering.
- `goto_tool_change_position` is described in two places with slightly different granularity: `tool-change` SKILL.md says "One approval, two `start_gcode_job` calls," while `TOOLS.md` says "two approved steps: Z up, then XY." I read this as one operator click covering both legs (consistent with the "one approval" wording and with `traverse_xy`'s per-leg `start_gcode_job` pattern), but "two approved steps" could also mean two separate confirm pages. This changes the approval count by one per tool change if I'm wrong.
- Nothing pins down what "7.5mm long including triple row threads" means in vendor terms (overall length vs usable reach vs some other segment) — this is inherent to the operator's own vague spec ("I don't have much more detail on it than that"), not a documentation gap, but it meant a real, unavoidable question rather than something resolvable by reading skills more carefully.
- The eight-controller list and the RPM/percent split are well documented, but nothing says what to do if the operator doesn't know which head is fitted either (beyond "ask") — I assumed asking again with a suggestion to physically look at the toolhead label would be the fallback, but that's a guess, not something the docs state.
- I had to guess that "get it converted and ready to run" should be read as authorizing staging of the whole eventual procedure (per motion law 6's resolution for a named procedure) rather than only the offline conversion step; the skill text ("A request to prepare or convert a file does not request a cut") argues the opposite reading for the cut itself, but doesn't clearly say whether it also caps the *tool-change* staging that must happen before a cut is even possible. I treated the tool-change as included in "get it ready to run" but still gated every individual step behind its own confirm-page click.
- I had to guess the branch counts in the "Counts" line (single hole, Flow A, no extra datum-probing) since the operator's message doesn't say how many holes exist or which tool-change flow they'll use; these were flagged as open questions rather than invented.
