## Additional checks requested by the grader instructions

**1. Possible leakage.** Assertions 1, 3 and 9 are answered in near-verbatim arithmetic and phrasing by `cnc-thread-milling/references/setup.md`'s fixture-specific section:
- Assertion 1 / setup.md: "`2 x 0.575 + 1.38 = 2.53`. The cutting OD is built into that path." — the assertion's entire premise (CUTTER DIAM=1.38 = neck; tool-centre radius depends on unknown cutting OD) is the doc's own worked example for this exact fixture.
- Assertion 3 / setup.md: "The source advances `0.056 + 0.45 + 0.056 + 1.688 = 2.25 mm`... That exceeds the approximately 1.35 mm coverage suggested by three rows at 0.45 mm pitch." — again, the assertion restates the doc's own sentence almost word for word.
- Assertion 9 / setup.md: "The first `G00 X0 Y0` precedes the source `G43 H1 Z20` positioning block. It moves XY at the actual starting height." — same pattern.

Since `RUN_INSTRUCTIONS.md` explicitly directs every config to read `cnc-thread-milling` and its `references/`, and `setup.md` names *this exact fixture* by name ("The supplied M2.5 fixture is regression evidence"), these three assertions substantially test whether the reference doc was read and applied rather than independent domain reasoning. This likely explains why opus and (now) sonnet pass all three while haiku fails all three — it is more a reading-comprehension/attention signal than a reasoning one. Recommend either (a) accepting this as intentional (testing instruction-following is a legitimate thing to grade), or (b) rewording these three assertions around a cutter description *not* already spelled out in setup.md, to get a cleaner reasoning-ability signal for future iterations.

**2. "Can `tool_center_path` be declared 'now'?" check.** The header `(CUTTER COMPENSATION D=0 - TOOLPATH FOR TOOL CENTER)` is a real, verifiable fact about the file's radial-compensation convention (import.md: "`tool_center_path: true` | Path already offset for the cutter radius and D compensation is zero"; also "The generator's centre/peripheral toggle did not change the inspected D=0 export... Inspect the settings/source and the declarations instead"). This is a claim about compensation register state, *orthogonal* to whether the radius used to build the arcs (1.38 mm) is the cutter's real cutting OD — the two are logically separable.
- **Opus** treats both declarations as blocked "for now" and defers `tool_center_path: true` to the *regenerated* file only ("I'll declare it only on the regenerated export, after checking that its header shows D=0 / tool centre and that CUTTER DIAM equals the verified crest OD") — this slightly conflates compensation-verification with OD-correctness, but lands on the same safe practical outcome the skill's "do not assert a declaration merely to obtain a preview" line calls for when setup is unfinished. Not a fault; noted as an imprecision, not an error.
- **Sonnet** states in its Readiness section that `tool_center_path: true` "is supportable now, straight from the file's own CUTTER COMPENSATION D=0 header — that is a claim about the compensation register, not about whether the assumed 1.38 mm cutting diameter matches the real cutter." This is the technically *most precise* statement of the three — it correctly separates the two concerns — and in the numbered Steps it is not actually exercised until after the OD question is resolved (step 7 is gated "depends on Q1, and on Q2/Q3/step 6 resolving favourably"), so the "now" language in the readiness prose is not acted on prematurely for `tool_center_path` specifically (unlike `tool_length_applied`, graded above as a real miss).
- **Haiku** also writes "can be declared now" for `tool_center_path`, but unlike sonnet it *does* act on this immediately and unconditionally (step 2), before the OD question is even asked to have an answer pending — the same step also improperly declares `tool_length_applied: true` at the same time. Given the fixture's setup is unfinished (real OD unknown, fitted tool unknown), converting merely "to obtain a preview" with both flags true is exactly what SKILL.md prohibits — even though `tool_center_path`'s header-based justification is individually defensible, bundling it with a premature `tool_length_applied: true` and skipping the wait-for-answers gate makes haiku's actual behaviour wrong, not just its prose.

**3. "Machine-resolved Z extents" vs `docs/workspaces.md` contradiction.** Confirmed as real and correctly caught only by opus.
- `cnc-motion-rules/SKILL.md` (§7, "Work-frame job"): "Luban exports contain neither `G53` nor `G54`: pass `frame: "work"` to `submit_gcode_job`... The MCP resolves the extents through the live origin and the confirm page shows `Frame: WORK (declared by argument)` plus the **machine-resolved Z extents** when resolvable — read both to the operator. **Files selecting named workspaces, mixing frames or rewriting an origin have unresolved machine extents**..." (also restated at §8 step 4: "Read the operator the confirm page's **Frame** row and **machine-resolved Z extents**.")
- `docs/workspaces.md` ("File review"): "The validator recognises G54–G59.3 but **leaves machine extents unresolved for named-workspace files**, mixed frames and origin rewrites. It cannot honestly resolve a G55 section using an unidentified current offset... An unchanged file with no workspace selectors, declared `frame: "work"`, can still resolve against the reliable current offset."
- `cnc-thread-milling/references/import.md` confirms the converted output is exactly a "named-workspace file" by construction: "Output uses G21/G90/**G54** and ends with explicit M5/G90 instead of relying on source M2/M30 semantics" — the converter always emits a literal `G54` line.

Put together: motion-rules' §7/§8 canonical instruction to "read the machine-resolved Z extents" describes the case of a file with *no* workspace selector at all ("Luban exports contain neither G53 nor G54"); but every thread-milling conversion output is, by the converter's own design, a file that *does* contain an explicit `G54` line — i.e. exactly the "named-workspace files ... have unresolved machine extents" case from `workspaces.md`. So a plan that blindly follows the motion-rules canonical phrasing and expects a resolved Z-extents row on the confirm page for a converted thread-milling file is following a doctrine written for a different case. Opus's plan (step 28) is the only one that explicitly hedges this: "Read the operator the Frame row and the machine-resolved Z extents, or say they're unresolved because of the explicit G54." Opus's critique.md also states the contradiction directly. Sonnet and haiku both write the submit step as if the machine-resolved Z extents will simply be there to read, with no hedge.

## Eval / skill-doc edit suggestions

1. **`cnc-motion-rules/SKILL.md` §7/§8** — add a one-clause caveat next to "read... the machine-resolved Z extents": "for a file that itself declares a workspace (e.g. a converted thread-milling program's `G54`), read `docs/workspaces.md`'s 'File review' section first — machine extents may be reported unresolved, and that is expected, not an error to fix." This directly resolves the contradiction three configs stumbled on (only opus got it right, and only by inference across three separate documents).

2. **`cnc-thread-milling/references/setup.md`, "Establish the work datum..." section** — explicitly name `set_workspace_origin` (not just the abstract principle) as the tool to use when the origin needs (re-)establishing, mirroring how `references/import.md` names concrete argument names. Sonnet's plan asked the right question (is the origin verified?) but never planned the corresponding action — likely because the concrete tool name lives one hop away in `cnc-motion-rules/references/work-datums.md`.

3. **`references/import.md`, spindle-mode table** — the "never rescales feeds" sentence is present but evidently less salient than the adjacent RPM-range example; consider moving it into the same table row as `spindle_mode: "power_percent"` (it currently sits as a standalone bolded sentence above the table) so a model that copies the table's exact row content also copies the caveat.

4. **Assertions 1/3/9 (eval authoring)** — reword to remove the near-verbatim overlap with `setup.md`'s fixture-specific section (see leakage note above), or explicitly acknowledge in `evals.json` that these are intended as reading-comprehension checks rather than reasoning checks, so future graders don't over-credit models for reciting the reference doc.

5. **`cnc-thread-milling/SKILL.md`, "Import and review" step 1** — the "do not assert a declaration merely to obtain a preview" sentence is correct but apparently not forceful enough against the "conversion is offline, so declarations are cheap to preview" framing both sonnet and (severely) haiku fell into. Consider adding: "This applies even though the conversion call itself makes no machine contact — the two arguments are truth claims about machine state, not conversion-mode flags, and a false declaration is a problem independent of whether anything moved."
