# Critique: Skills and documentation for external thread-milling with multiple bosses

## What helped

- **`cnc-motion-rules` SKILL.md (sections 0–8, law 6, law 8, appendix A):** Clear authority rules and motion law hierarchy for staging jobs, approval handoff pattern (stage → URL → end turn → wait), and abort/completion Z retreat behavior. The canonical calls with exact argument names eliminated guessing about field order and parameter names. The `traverse_xy` refusal for sub-floor XY motion is explicit and applies to multi-feature routing.

- **`cnc-thread-milling` SKILL.md (setup, import and staging sections):** Clearly states "one program per feature with that feature's XYZ work datum" and the consequence: "do not concatenate source programs." This directly addressed the two-boss scenario. The human-gated workspace tool (`set_workspace_origin`) pattern is clear; preference for one WCS across indexed rotary operations supports the common-datum use case here (no rotary indexing, but same principle).

- **`cnc-thread-milling/references/setup.md` (multiple holes/bosses section):** Explicit approval count formula ("Six holes and two flow-A tool changes normally mean 6 + 4 + 4 = 14 approvals") and the rule that read-only calls/conversion do not add approvals. This enabled an accurate count for this task: 2 jobs = 2 approvals, no tool change flow needed.

- **`cnc-thread-milling/references/import.md` (controller selection table):** Okuma dialect mapping is documented with specific transformations (G15 H1 → G54, G56/H removed). No guessing about whether a Fanuc conversion would work for Okuma exports.

- **TOOLS.md (convert_thread_milling_gcode, submit_gcode_job, validate_gcode):** Precise argument schema with exact field names, the distinction between offline conversion (no approval) and staging (approval required), and the three-step flow (convert → validate → submit). The note that `source_controller` must match the actual generator dialect, not trial-and-error, is practical.

- **work-datum selection and verification (cnc-motion-rules/references/work-datums.md, sections on "Reuse one WCS across indexed rotary operations" and "Multiple workspaces are frowned upon"):** The phrase "one verified WCS can serve B0, B90, B180 and B270 cuts" and the warning against creating workspaces "simply for each B angle" directly support the decision to use a single G54 for both bosses at (20,15) and (70,15).

## What was missing or unclear

- **Initial motion-floor preflight for multi-feature transit:** The RUN_INSTRUCTIONS require a preflight check (section 0, item 2: "frame"), but the landmark check is not explicit for transits between separate features with a common datum. The plan includes a traverse check at step 10, but earlier guidance on whether to check landmarks proactively at preflight (step 1) could be clearer. The work-datum reference does not detail landmark interaction for a common G54 shared by two features 50 mm apart on the work frame.

- **Actual position after a file job completion:** `cnc-motion-rules` law 8 states "A COMPLETED `run_tool_setter` ends the same way ... raised straight up to the traverse height," but for file jobs (gcode) the final Z is less prescriptive: "the documented Snapmaker file-job completion raises at the finish XY, but the source's work Z20 alone proves nothing about actual final machine Z." This is correct guidance to re-read position (step 7), but it means the operator must communicate the actual final position or we re-read it. The note "A stopped job does not retract" is clear; completion is less deterministic.

- **Spindle mode / head selection detail:** The thread-milling import reference states "The converter never chooses spindle mode" and documents `cnc_200w_rpm` vs `power_percent` options, but the criteria for detecting which head is fitted at runtime (head identity check at `get_machine_profile`) is not spelled out in the skill examples. The note "If connected identity is null, ambiguous or disagrees with the operator, ask which head is fitted" is advice to ask the operator; the dry-run prompt stated "standard CNC head is fitted, chosen power 65%," so we trust that statement. A tighter connection between `get_machine_profile.connectedHead.toolHead` identity and the spindle-mode choice would help.

- **Work-frame feature-centre coordinates in a multi-boss program:** The setup reference says "generate one program per feature with that feature's XYZ work datum" and gives an example (work zero at plate corner, hole at work (10,10) needs that generator XY datum). The implication is that the feature centre is the work datum, not the origin corner. For the two bosses, the prompt states "common corner datum" and "per-boss datums (20,15) and (70,15)." The plan interprets this as: G54 origin is the common corner, boss1 feature datum is work (20,15), boss2 is work (70,15). This is consistent with the skill, but an explicit example in the import reference (or thread-milling.md) of "common datum at corner, two features at (X1,Y1) and (X2,Y2)" would remove the need for this interpretation.

## What was guessed or inferred

- **Traverse between features at step 10:** The prompt says "common corner datum" but does not specify machine coordinates for this reference or the exact work origin offset. The plan assumes that after the first job completes at work Z20 (final rapid retract per the source), the motion-floor check for the second job and the traverse to (70,15) will be gated by the live `get_position` and landmark checks at that time. If landmarks block the direct path, a separate approved traverse (step 10) is included. This is inferred from cnc-motion-rules law 2 (XY transport at or above the motion floor) and law 4 (landmarks are obstacles), but the actual need for a traverse approval depends on the live position and the source program's first move.

- **Order of questions vs conversion:** The plan batches three preflight questions into step 1 (before any conversions). This follows cnc-motion-rules law 7 ("ask once") and the pattern that all unknowns should be resolved before any motion or staging. The RUN_INSTRUCTIONS state "Questions for the operator (one message)" in the plan format. Three questions fit this; they address order, inspection timing and landmark verification, all of which shape the approval sequence but do not block the offline conversion flow itself.

- **Okuma vs Fanuc source dialect:** The prompt states "two complete Okuma thread-milling exports." The import reference lists `okuma` as an accepted controller value. The plan assumes `source_controller: "okuma"` for both conversions. If the actual exports are in a different dialect (e.g. the operator copied from a Fanuc example and edited), the conversion will fail with a dialect mismatch. The skill documentation does not include a "how to detect the export dialect from the file text" section, so the plan trusts the operator's statement and would re-ask if a conversion refusal occurs.

- **Spindle power percentage is application-specific:** The prompt states "feeds were generated for the verified speed at that setting" (65%). The plan takes this to mean the cutter, material, cutting conditions and feeds were all chosen/validated at 65% standard-head power. A different power setting would require feed recalculation, not just a converter parameter swap. This inference comes from the general principle in cnc-thread-milling (setup.md): "Use tool data and the operator's setup; no universal feed, pass count, safety distance or spindle percentage." The plan does not re-ask for feed recalculation; it trusts the 65% setting is correct.

## Summary

The skills and documentation are well-structured for this task. The main clarity gap is the interaction between multiple features sharing a common work datum and the multi-workspace-avoidance guidance; an explicit worked example in the import reference (two bosses, one corner datum, separate programs) would make the workflow faster. Spindle-mode detection and feature-coordinate semantics required careful reading across three documents (TOOLS.md, import.md, setup.md) but are not contradictory. The preflight and approval flow is sound once the motion-rules foundation is loaded first.
