## Docs contradiction check

**`goto_tool_change_position` approval count — real, and it explains haiku's miscount.** `src/server/services/mcp/docs/TOOLS.md`: *"`goto_tool_change_position` — two approved steps: Z up, then XY to the operator-set park spot."* `.claude/skills/tool-change/SKILL.md`: *"Flow A is four approvals — measure old, park, measure new, apply — each announced"* and, more specifically, *"**Park** — `goto_tool_change_position`. One approval, two `start_gcode_job` calls: Z rises to the park height first, then X/Y."* These two documents genuinely disagree on how to *count* the same action: TOOLS.md's plain-language description ("two approved steps") reads as two separate confirm-page approvals, while tool-change/SKILL.md explicitly declares park to be **one** approval that happens to require two `start_gcode_job` calls. Opus and sonnet both followed the skill's explicit count (park = 1, matching "flow A is four approvals" and their own 5-total tool-change+file-job counts). Haiku instead followed TOOLS.md's phrasing literally, splitting park into `[2 APPROVALS]` and arriving at 5 (not 4) approvals for the tool-change block alone — a direct, traceable consequence of trusting the less specific document over the task-scoped skill. **Edit suggestion:** `TOOLS.md`'s `goto_tool_change_position` line should either say "one approval, staged as two `start_gcode_job` calls" (matching the skill's accounting) or the skill should stop calling it "one approval" if two separate confirm pages really are shown — right now an agent that reads only one of the two documents gets a different, internally-consistent-but-mutually-contradictory count.

**Confirm-page "machine-resolved Z extents" vs `docs/workspaces.md` for explicit-G54 files — not a real contradiction, but worth tightening.** `TOOLS.md`'s `submit_gcode_job` entry: *"The confirm page shows Frame and machine-resolved Z extents when resolvable. Named workspace selectors, mixed frames and origin writes leave machine extents unresolved..."* Read in isolation, "named workspace selectors" could be misread to include a plain `G54` (which is, after all, a named workspace selector in the G-code sense). `workspaces.md`'s "File review" section resolves this: *"The validator recognises G54–G59.3 but leaves machine extents unresolved for **named-workspace files**... It cannot honestly resolve a **G55** section using an unidentified current offset. ... An unchanged file with no workspace selectors, declared `frame: 'work'`, can still resolve against the reliable current offset."* The concrete example given is G55 (an alternate WCS whose offset isn't known from live state), not G54 (the default WCS that matches the machine's current live offset). Since `import.md` confirms the thread-milling converter's output always emits `G54` (never G55-G59.3), a converted thread-milling file is exactly the case the docs *do* resolve extents for, not the case they leave unresolved. Opus's and sonnet's plans both rely on reading "Frame and machine-resolved Z extents" off the confirm page for the submitted file (opus step 16, sonnet step 25) — this is correct, not a gap in either plan. **Edit suggestion:** `TOOLS.md` line 24 should say "named workspace selectors *other than the currently-active G54*" (or similar) to remove the ambiguity, since as written it is easy to conflate "G54 is technically a named selector" with "G54 leaves extents unresolved," which it does not per `workspaces.md`'s own worked example.

## Edit suggestions for the skills / docs

1. **`cnc-thread-milling/references/setup.md`, "Keep the dimensions separate"** — add one explicit sentence next to the D4/50L row warning that a thread's *nominal* major diameter (e.g., "M4" implying 4 mm) is **also** not a substitute for the measured cutting-crest OD. The table already separates cutting OD from neck and shank, but nothing in it says "don't use the thread's own major-diameter number either" — which is precisely the invented value haiku used. The M2.5 regression section shows the *neck* trap but not the *nominal-diameter* trap; a parallel sentence there would close this specific gap.
2. **`TOOLS.md`, `goto_tool_change_position` line** — reconcile the "two approved steps" phrasing with `tool-change/SKILL.md`'s explicit "one approval, two `start_gcode_job` calls" / "flow A is four approvals" accounting (see Docs contradiction check above). Pick one convention and use it in both places.
3. **`TOOLS.md`, `submit_gcode_job` line ("named workspace selectors... leave machine extents unresolved")** — clarify that this excludes the currently-active default `G54`, consistent with `workspaces.md`'s G55 example and the "no workspace selectors... resolve against the reliable current offset" sentence. As written it's ambiguous enough that a careful agent has to cross-reference a second file to be sure a converted (G54-only) thread-milling job's Z extents will actually show.
4. **RUN_INSTRUCTIONS.md / the plan template** — consider spelling out, in the template itself, that `-- end turn --` must appear immediately after *every* `[APPROVAL]`-tagged step, not just once per document. Both opus and sonnet do this correctly by convention, but nothing in the template enforces it, and haiku's single end-of-document marker was accepted structurally even though it defeats the confirm-and-wait pattern for every approval before the last one.
