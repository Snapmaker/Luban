# Critique: thread-milling, M4 single-form cutter (dry run)

## What helped

- **thread-milling.md, "Usage" and "The two required declarations".** Clear about what `tool_center_path` and `tool_length_applied` mean. That is what showed a tool change has to come before the job, because the probe is fitted now.
- **thread-milling.md, "Generator option coverage".** Mapped directly onto the Machining Doctor inputs: Single tooth, D=0 tool centre, Fanuc, precision, XYZ datum, and "flutes vs axial forms are independent". The last one stopped me treating "single thread" as a flute count.
- **thread-milling.md, spindle paragraph and "Firmware evidence".** The 8000–18000 RPM refusal for 200 W, and the standard head's P-percent with no feed rescaling, gave a clean branch on `get_machine_profile`.
- **thread-milling.md, "Review ... tool-centre bounds, not a swept cutter/holder clearance ... exclude the unknown initial position".** Showed me the neck/shank clearance and the program's first `G00 X0 Y0` are outside what any check covers. That's why the plan uses `goto_work_origin`.
- **cnc-motion-rules §0 item 7 and §7, and tool-change "Two flows".** Gave the one-question-batch shape and the file-job recipe (`frame: "work"`, read the Frame and Z-extents rows).
- **The fixture itself.** Reading it exposed the 1.38 "cutter diam" vs the operator's "1.38 mm neck", and the 2.25 mm cutting length vs "triple row".

## What was missing, unclear or contradictory

1. **No skill covers thread milling.** None of the four skills mentions `convert_thread_milling_gcode`, and TOOLS.md ("54 tools") doesn't list it. It exists only in the README's last section and in docs/thread-milling.md. An agent working from the skills alone wouldn't find it. It belongs in cnc-motion-rules §7 (a program someone else generated) or in its own skill, with the order: convert → tool change → submit.
2. **Order of `tool_length_applied` vs the tool change.** thread-milling.md says the work origin "already accounts for the fitted tool tip", but not what to do when the wrong tool is fitted. I had to decide myself that converting early is fine (it's offline) as long as submitting waits until after `apply_tool_length_offset`. The doc should say this, or the converter should only be called after the change.
3. **`head_type` on `submit_gcode_job`.** thread-milling.md says `head_type: "cnc"`, but TOOLS.md lists `head_type?` without its values, and nothing says whether it should be `"cnc_200w"` or the like on a 200 W head. I guessed `"cnc"`.
4. **What the tool-change skill doesn't settle.** It asks "whether the work origin was set with the tool now fitted", but has no guidance for when Z0 was set by a tool that is neither the old nor the new one, and has no setter measurement. I added a stop branch (Z0 set again by the operator), but that is my reasoning, not doc text.
5. **The program's initial position.** thread-milling.md says the converter "does not invent clearance" and validation excludes the start position. It doesn't say whether `submit_gcode_job` checks the first XY leg against landmarks. Pre-positioning with `goto_work_origin` is my own safety step and costs an extra approval. The docs should say whether it's required or redundant.
6. **Hole-centre accuracy.** Nothing links the generator's centre plunge to how exactly the origin has to be placed, even though a thread-mill-in-tap-drill clearance is about 0.1 mm. `probe_circle` args aren't listed anywhere I was allowed to read. The cnc-probing skill gives only the requirements (min/max diameter, measured top), so branch 3a has no exact argument names. There is also no `circle` op in `probe_program`, so "find the top, then circle" costs two approvals. And the MCP can't write work XY, so a measured centre can only reach the origin through the operator. The docs don't say whether comparing against `goto_work_origin`'s machine destination is the intended check. I guessed that it is.
7. **Machining recommendations.** thread-milling.md deliberately makes none. So radial passes (I suggested 2), feed per tooth and cutting speed for a light machine in aluminium are guesses with no guidance. A standard-head RPM figure is also absent, so Q6 asks the operator.
8. **Tool-setter `bit_length_mm` for the probe.** §8 uses 70 in its example while the stored effective length is 71.3. The tool-change skill says "declare it low". I used 70. Whether a thread mill's fragile single tooth is OK on the setter switch isn't mentioned.
9. **Crash alarm with the probe removed.** Law 5 says an unexpected probe-channel trigger during motion is a crash. None of the tool-change docs say what to do with the removed probe (leave it plugged in and still? unplug it?) while a file job runs.
10. **Minor.** The README says the rig was "hardware-verified ... 200 W toolhead", which tempts an agent to skip `get_machine_profile`. I treated it as history.
