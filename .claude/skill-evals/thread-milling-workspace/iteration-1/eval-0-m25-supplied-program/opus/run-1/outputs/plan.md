# Plan: Regenerate the M2.5x0.45 program for the real cutter, convert it, carry the work origin from the probe to the thread mill, and stage one file job

## Findings before anything moves

- **The program was generated for the neck diameter, not the cutting diameter.** Header: `CUTTER DIAM=1.38`, `D=0 - TOOLPATH FOR TOOL CENTER`. The helix is `G03 Z0.45 I-0.575 J0`: a tool-centre radius of 0.575, and 2 x 0.575 + 1.38 = 2.53 = the programmed major diameter. So the cutter diameter is built into the path. The operator says 1.38 mm is the *neck*. On a thread mill the teeth are wider than the neck; for M2.5x0.45 I would expect a tooth diameter of roughly 1.9 mm, but that needs measuring. With a 1.9 mm cutter this path cuts to a major diameter of about 1.15 + 1.9 = 3.05 mm, about 0.5 mm oversize (the whole thread depth is about 0.24 mm radially). The straight lead-in at F2159 would also drive the teeth about 0.3 mm into the wall. That strips the thread and very likely snaps a 1.38 mm neck. `tool_center_path: true` is a correct declaration for the file, but it is only safe once the path was computed for the real tooth diameter. **The supplied file must not be staged. It must be regenerated.**
- **The cutting length doesn't match "triple row".** The header says `L=2.25 [MULTI TOOTH]`, which is 5 rows at 0.45. The program makes 3 passes and each pass rises 0.056 + 0.45 + 0.056 + 1.688 = 2.25 mm. If the cutter really has 3 rows of teeth, its cutting length is about 3 x 0.45 = 1.35 mm, and each pass would leave about 0.9 mm of unthreaded wall. That gives an incomplete thread. Per thread-milling.md, "triple flute" does not tell us the tooth rows ("do not infer one from the other"), so the operator has to count the crests.
- **Depth margin is thin.** The deepest tool-tip Z is work Z-5.056 (5 mm thread plus lead-in). A hole "about 6 mm" deep leaves about 0.94 mm below the tip if 6 mm is full-diameter depth. If 6 mm includes the drill point, a 118 degree point on 2.05 mm is about 0.6 mm tall, so the full-diameter depth is only about 5.4 mm and the margin drops to about 0.3 mm. Worth asking.
- **The touch probe is in the spindle, not the thread mill.** Both the tool change and the `tool_length_applied: true` declaration depend on this. That declaration says work Z0 already refers to the fitted tool's tip. Right now it would refer to the probe (if the probe set Z0 at all). The declaration only becomes true after a tool change that carries the origin to the thread mill: tool-change flow A, the touchscreen wizard (flow B), or the operator re-zeroing Z with the thread mill. Running M3 with the probe fitted would destroy it. The file job is staged only after the swap is verified.
- **XY has to be the hole centre, and the probe can't find it.** The program cuts around work X0 Y0. The probe tip (about 2.5 mm per README jig facts) can't enter a 2.05 mm hole, so `probe_circle` isn't possible. With a 1.9 mm cutter in a 2.05 mm hole, a concentricity error of about 0.07 mm touches the wall on the plunge. XY trust can only come from the operator: the hole was drilled at this work X0 Y0 in this clamping, with no re-clamp or XY re-zero since. If the hole sits elsewhere, the fix is to regenerate with that XY datum (the generator supports a nonzero datum). I don't hand-translate the file or write the origin.
- **Spindle mode depends on the head, which is not in the stand-in.** The source runs `S17991`. On the 200 W head, `cnc_200w_rpm` keeps 17991, which is inside 8000-18000. On the standard head, `power_percent` replaces RPM with P% and does **not** rescale feeds. The Snapmaker listing puts the standard 50 W head at about 12,000 rpm maximum (the operator should confirm). Feeds calculated for 18,000 rpm would then run about 1.5x the chip load on this cutter, so on that head the regeneration must also set the generator's maximum RPM to the head's limit. `get_machine_profile` is read first, and the plan branches on it.
- **The first move is the program's own XY rapid at whatever Z the head is at.** The source order is `G00 X0 Y0 ... M03`, then `G43 H1 Z20` (the converter keeps the Z20 and drops H1). Validation leaves out the unknown start position. So the job has to start with the head at the park height, machine Z328, and it will: `run_tool_setter` ends at Z328 (`result.finalZ`). The segment from the setter (machine X79 Y293) to the hole must also pass the `rotary` landmark (X110-230 Y130-342) at 328. I re-read `requiredToolheadZ` after the thread mill is measured and it must be at or below 328. Every other XY move in the program is within about 1.2 mm of the hole centre (fine positioning inside the hole), so law 2 holds.
- **What the converter will change (expected, to read back to the operator):** `M06 T1` removed (the tool must already be fitted); `G43 H1` removed with the Z20 move kept; `G40/G41 D1` removed (D1 is a register, and the value is 0); `M08` removed, since coolant isn't controlled, so any cutting fluid in the blind hole is the operator's hands; arcs become G1 chords at 0.002 mm; `M30` becomes an explicit `M5`. The final cut ends at work Z+0.006 (source rounding, kept as-is), then `G0 Z20`, and the interpreter returns to Z top at the finish XY.
- **Measuring the probe as the "old tool" on the setter trips the probe channel.** Per motion-rules §8, that measurement needs `accept_probe_contact: true`, otherwise it is an undeclared contact and a crash alarm. Once the probe is removed, its pill should read no-contact. A stray probe-channel trigger during the file job is a crash stop partway through the thread, and the cut can't be resumed.
- **Expected validator warning:** a spindle-on Z below 0 (work -5.056). That is the thread depth, it's intended, and the operator is told so. It is not a reason to edit the file.
